Part 0

The big idea

Pragmatic is a black-box recorder for LLM agents, written in Rust. Two promises: if an agent crashes 900 steps into a 1,000-step job, it resumes on step 901 without re-paying for a single token; and when someone asks "what did the agent actually do?", the entire run replays bit-for-bit from a tamper-evident log, with the model never contacted.

Both promises come from one trick, and every file in this repository exists to serve it:

  1. An LLM call is treated as a draw from a probability distribution. The code calls this the Oracle.
  2. Every realized draw — plus every side effect, message receive, and clock read — is appended to a log the moment it happens. The log is the Journal, and each entry is hashed together with the previous entry's hash, forming a chain.
  3. Crash recovery and audit replay are now the same operation: run the agent function again from the top, but feed it recorded outcomes from the journal instead of sampling the model. Editing any journal entry after the fact breaks the hash chain at exactly that spot.

There are only four names you need to keep in your head. Everything else is supporting cast.

NameWhat it is
Oraclethe LLM call, as a swappable trait — the only source of randomness
Journalthe append-only, hash-chained log where every outcome is saved
Ctxthe handle your agent function holds; ctx.oracle(...) decides record-vs-replay
Runtimethe driver: run, resume, replay, verify

How the workspace fits together. The core crate (pragmatic) has zero dependencies and contains the whole mechanism. Around it: two adapters that plug real model APIs into the Oracle trait, a macro that stamps your agent's code version into the journal, a CLI for inspecting journals, and a C ABI that carries the runtime into five other languages.

How to use this guide. This guide assumes nothing. If you have never written Rust, start with Part 1 — it teaches exactly the Rust needed to read this codebase, using only code from this repo, and you can jump back to it any time a symbol looks unfamiliar. The mechanism itself lives in Parts 2–4 (the core crate); every later part is a wrapper around it. Each file gets: a plain-words walkthrough with real code from the repo, the one thing to remember, the Rust patterns in play, and the questions someone will eventually ask you about it — with honest answers, including the known trade-offs. Being upfront about a documented trade-off is the defense.

Part 1

Just enough Rust to read this guide

This part exists so you never have to leave the guide to look something up. It teaches exactly the Rust you need to read this codebase — nothing more. Read it once now, then come back to it whenever a later section uses a symbol you don't recognize. Every example below is real code from this repo.

What you're looking at — a workspace of crates

A crate is Rust's word for a package: one library or one program. This repo is a workspace: seven crates that build together, listed in the Cargo.toml file at the root. Cargo.toml is the manifest — name, version, dependencies — and Cargo is Rust's build tool that reads it.

Inside each crate, the code lives in src/. Two special filenames: src/lib.rs means "this crate is a library" (code for others to use), and src/main.rs means "this crate is a program you can run" (only pragmatic-cli has one). The target/ folder is just build output — machine-generated, never read it.

One more word you'll see constantly: stdlib (standard library) — the toolbox every Rust program gets for free: files, strings, networking. "Zero dependencies" means the core crate uses only that toolbox.

Structs — data with a name

A struct bundles data under a name:

pub struct Value(pub Vec<u8>);

In plain words: "a Value is a Vec<u8> — a growable list of bytes — wrapped in a new name." Wrapping one thing in a new name is called a newtype; it exists so the compiler treats "journaled bytes" as its own kind of thing, not just any bytes. pub means public — visible to code outside this file. The wrapped value is reached as .0 (field number zero).

Enums — a value that is one of a fixed list

A Rust enum is a type that must be exactly one of several named options — and each option can carry data:

pub enum Fault {
    OracleErr(String),
    Timeout,
    BudgetExhausted,
    JournalDesync { cursor: Cursor, expected: String, found: String },
    // ...
}

In plain words: "a Fault is either an oracle error carrying a message, or a timeout carrying nothing, or a desync carrying three named fields, or …". This is how the codebase makes lists of possibilities airtight: every failure must fit one of these boxes.

You take enums apart with match:

match fault {
    Fault::Timeout => Decision::Restart,
    Fault::JournalDesync { .. } => Decision::Stop,
    _ => Decision::Escalate,
}

The compiler forces you to handle every option (_ means "everything else"). When the guide says "the supervisor dispatches on the fault tag," this is the machinery it means.

Traits — a job description any type can apply for

A trait is a list of functions a type promises to provide. It's the single most important concept for this codebase:

pub trait Oracle {
    fn call(&self, prompt: &Value) -> Result<Value, Fault>;
}

In plain words: "anything calling itself an Oracle must have a call function that takes a prompt and returns either a Value or a Fault." A type applies for the job with an impl block: impl Oracle for AnthropicOracle { ... } says "the Anthropic client is an Oracle — here's its call."

This is why the runtime never cares which model you use. It's written against the job description, not the applicant:

pub struct Runtime<O: Oracle> { /* ... */ }

The <O: Oracle> part is a generic: "this runtime works for any type O, as long as O is an Oracle." Real model, fake test model, model that refuses to answer — all interchangeable.

Result and ? — errors as values

Rust has no exceptions. A function that can fail returns a Result, which is just an enum: Ok(the answer) or Err(the problem). The ? operator is the shorthand that makes this bearable:

let plan = ctx.oracle("plan the task")?;

In plain words: "call the oracle; if it worked, unwrap the answer into plan; if it failed, stop here and pass the error up to whoever called me." Every ? you see is a tiny early-exit. A cousin you'll also see: Option — Some(value) or None — for "might not exist" rather than "might fail."

Ownership and borrowing — the & and &mut everywhere

Rust's defining rule: every value has exactly one owner, and when you want to let someone else look at it, you lend it — called borrowing:

  • &thing — a shared borrow. Read-only. Any number of readers at once.
  • &mut thing — an exclusive borrow. The borrower may change the thing, and while they hold it, nobody else may even look.

That's why every agent function has this exact signature:

fn research(ctx: &mut Ctx) -> Result<Value, Fault>

The agent borrows the context exclusively: it can append to the journal through it, and the compiler guarantees no one else touches the journal mid-step. When you see an apostrophe like Ctx<'a>, that's a lifetime — a label the compiler uses to prove a borrow never outlives the thing it borrows. You can read every lifetime in this codebase as: "this handle must not outlive the run it belongs to." You never need to write one to read the code.

Strings, while we're here: String is owned text, &str is borrowed text (a view into someone else's), and Vec<u8> is raw bytes. The journal stores bytes, not text — models can return anything.

Closures — functions you write inline

A closure is an unnamed function defined right where it's used, with its arguments between pipes:

ctx.effect("charge_card", amount, |arg| do_the_charge(arg))

In plain words: "here's a side effect named charge_card; and here, inline, is how to perform it if the runtime decides it actually needs performing." The runtime holds the closure and only invokes it when recording — during replay it's never called. The C layer (called the FFI — "foreign function interface," how Rust talks to other languages) and the bindings pass the same idea across languages as "callbacks."

Attributes — instructions to the compiler, in brackets

Lines starting #[...] are attributes: notes attached to the next item.

  • #[derive(Clone, PartialEq, Eq)] — "compiler, auto-write the code that makes this type copyable and comparable." Free standard behavior, zero hand-written code.
  • #[cfg(feature = "macros")] — "only compile this if the macros feature is switched on." Conditional compilation.
  • #[pragmatic::durable] — a procedural macro: a program that runs at compile time and rewrites your function's code (here: injecting the version-stamp line). That's the whole pragmatic-macros crate.
  • #[doc(hidden)] — "this is public but keep it out of the documentation" — used for test helpers.

unsafe — the clearly-marked trapdoor

Rust's compiler normally proves your memory use is correct. An unsafe block says: "compiler, you can't check this part — a human takes responsibility." In this codebase, unsafe appears only where Rust must talk to other languages (the C ABI and the Python binding), because foreign code is invisible to the compiler's proofs. Every such spot pairs the trapdoor with a guardrail — for example, the context pointer handed to C is deliberately nulled after each run, so misuse fails with a clear error instead of corrupting memory. When you hit unsafe in Part 6 or 7, the question to ask is always "what's the guardrail?" — and the guide answers it each time.

Running things — the three commands that matter

cargo test

Runs every test in the workspace — including the code examples inside documentation comments. This is the repo's proof machine.

cargo run --example research_agent

Runs one of the examples/ programs (each crate's examples/ folder is runnable demos). The best way to feel the crash-resume trick is to run one, kill it mid-run with Ctrl-C, and run it again.

cargo build -p pragmatic-ffi

Builds one specific crate (-p = package) — here, the shared library the C++, Go, Java, and Node bindings load.

The one thing to remember. You now know every symbol this codebase uses: structs bundle data, enums list possibilities, traits are job descriptions, Result + ? carry errors, &mut is an exclusive loan, and unsafe is a marked trapdoor with a guardrail. Everything else is vocabulary you can look up right here when you meet it.

Part 2

Core crate I — the foundations (value, fault, sha256, journal)

These four files are the ground floor of the pragmatic crate — everything else is built on top of them. value.rs defines the bytes every recorded step carries, fault.rs lists every way a run is allowed to fail, sha256.rs provides the fingerprint function that makes the log tamper-evident, and journal.rs combines all three into the append-only log that the product's replay and audit story rests on. Read them in that order.

01lib.rsthe front doorcrates/pragmatic/src/lib.rs

This is the first file the compiler reads, and it's the front door of the whole library: it describes what Pragmatic is, lists the other files, and puts the important names where users can reach them. Nothing is computed here.

Its best feature: the description at the top contains a working code example, and Rust actually runs examples inside documentation as tests. So the product's core promise sits at the top of the codebase as a program that fails the build if it ever stops being true:

let resumed = rt.resume("research-42", research).unwrap();
assert_eq!(resumed.fresh_steps, 0); // everything came from the journal

That last line is the whole pitch in code: after a crash, the run resumed and made zero new model calls — every answer came from the saved log.

The rest of the file is housekeeping: a list of the crate's other files, and a "shortcut menu" that lets users grab the four main types (Oracle, Journal, Ctx, Runtime) directly without knowing which file each lives in.

Remember

The product's core promise is written into this file as a test that runs on every build.

Questions you might get asked

Q: How do I know the crash-recovery claim actually works? A: It's not just in the marketing — it's an assertion in the code that runs automatically on every test cycle. If recovery ever re-called the model, the build would fail. Q: Where do I start reading the code? A: Right here. This file is a table of contents; the four names it exports are the whole story, and this guide covers each one in order.

02value.rsthe bytes every journaled step carriescrates/pragmatic/src/value.rs

Value is the box every recorded outcome travels in: a model's answer, a message received, a tool's result. The whole definition is one line:

pub struct Value(pub Vec<u8>);

In plain words: a struct wrapping a single list of raw bytes (Vec<u8> is Rust's "list of bytes"). That is all it is, on purpose. Think of it as a sealed envelope — the journal must be able to store an outcome and later hand it back byte-for-byte without ever opening it. There are helpers for viewing the bytes as text when a human wants to look, but the bytes are always the real record: they are what gets saved and hashed.

Remember

Value is opaque bytes on purpose — the journal's byte-for-byte replay guarantee only works because nothing ever interprets the payload.

Questions you might get asked
  • Why raw bytes instead of text? Because an outcome is not always clean text — a tool result could be anything. Storing bytes keeps replay exact and leaves interpretation to whoever needs it.
  • Could a strange character in a model's answer corrupt the record? No. The bytes are what gets saved and hashed; the text view is display-only, and at worst a log line shows a placeholder character.
  • Can I put anything in a Value? Yes — any byte string is valid, which is why the inner field is public. There is no hidden rule to break.
03fault.rsevery way a run is allowed to failcrates/pragmatic/src/fault.rs

This file is one enum — a fixed multiple-choice list — naming every way an agent run is allowed to fail: the model call failed, a tool failed, time ran out, a step or cost budget ran out, the agent tried something it had no permission for, and so on. The philosophy: failures are named values, not crashes. It is the runtime's incident report form — every failure mode has a pre-printed box, and the Supervisor reads the box to decide what happens next.

Two entries matter most for the replay story. JournalDesync means the log and the code disagree — usually the agent code changed between recording and replay — so the run fails loudly rather than pretending. ReplayExhausted means the log simply ended: nothing is wrong, and "resume" is the right verb to continue the run, because "replay" refuses to call the model.

Remember

Fault is a closed, matchable list — supervisors make decisions by matching on the tag, so every failure must fit one of these boxes.

Questions you might get asked
  • What actually happens when an agent fails mid-run? The failure becomes one of these named values, and the Supervisor picks a rule for that name — retry, undo, or restart from the journal. Nothing dies silently.
  • Why a fixed list instead of a general-purpose error type? Because decisions are made by the name on the box, and a closed list means the compiler forces the Supervisor to handle every case — nothing falls through unclassified.
  • Why do faults carry a text message instead of full error details? So faults can be copied, stored, and compared, which tests and supervisors need. The deliberate trade-off is losing some machine-readable detail.
04sha256.rsthe in-house fingerprint functioncrates/pragmatic/src/sha256.rs

This file is a from-scratch copy of SHA-256, the industry-standard hash function — a function that turns any pile of data into a short, fixed-size fingerprint — plus HMAC-SHA-256, the keyed version, which mixes a secret key into the fingerprint. The journal's tamper-evidence rests on these fingerprints.

It exists for one reason: the core crate takes zero outside dependencies, so rather than pull in a crypto library, the standard algorithm was re-typed here. Correctness does not rest on trusting the author — the unit tests check the code against the official published test answers, so any deviation from the standard makes those tests fail. The keyed version is what makes an audit trail attributable to the runtime's key, not just tamper-evident.

Remember

This is not invented crypto — it is the standard algorithm, re-typed to keep the crate dependency-free, and pinned to official test vectors.

Questions you might get asked
  • Isn't "rolling your own crypto" a red flag? The warning is about inventing new schemes, not transcribing a standard hash, and the official test vectors pin this code to the spec. The honest trade-off: a vetted library gets more outside review and hardware acceleration — this buys zero dependencies at the cost of raw speed and outside eyes.
  • Is a software-only hash fast enough? Yes for this workload — measured journal appends run at roughly 0.44 microseconds each at a million entries on an Apple M5 Pro, in release builds — and the cost stays flat from a thousand entries out to a million.
  • Any known weak spots? One, worth naming: the signing key is not wiped from memory after use. That is acceptable when the same process holds the key anyway, but it is the kind of thing an audit should note.
05journal.rsthe append-only, hash-chained flight recordercrates/pragmatic/src/journal.rs

The Journal is the crate's load-bearing file — the black-box flight recorder of an agent run. Every outcome decided by the outside world — a model's answer, a message, a tool result — is appended as it happens; replay reads them back instead of calling the model again.

Each entry's fingerprint bakes in the previous entry's, so changing any committed entry breaks every later link. A crash mid-write only tears the tail, which gets trimmed on reopen, and the run resumes from the clean prefix. Tool calls are logged as an intent before and a commit after, so a crash in between leaves a visible loose end for recovery; the agent code's fingerprint is logged too, so changed code fails loudly on replay.

Remember

The journal is the single source of truth — replay, crash recovery, and audit are just different ways of reading this hash-chained list back.

What the tests prove

A thousand test runs (each using a predictable fake model — “seeded” with a fixed starting number) replay with zero model calls and identical results; runs crashed at every point resume with only lost steps re-called; and append cost stays flat out to a million entries.

Questions you might get asked
  • If someone edits the log, do you catch it? Casual edits, yes — verification pinpoints the first bad entry. But an attacker could rewrite everything and recompute: unkeyed, the log is tamper-evident, not tamper-proof; the keyed mode closes that gap for anyone without the runtime key.
  • What if the machine dies mid-run? The torn tail is trimmed and the run resumes from what was recorded, re-calling the model only for the lost steps.
  • Why read the whole file into memory on open? The whole chain is verified on load, and journals are per-run logs, not databases — simple and safe. Streaming would be the upgrade if they grew huge.
Part 3

Core crate II — the execution engine (oracle, ctx, store)

These three files are the engine room. oracle.rs defines the one and only place randomness is allowed to enter a run (the LLM call), plus a small toolkit of wrappers around it. ctx.rs is the referee your agent code actually talks to: for every step it decides "read the saved answer from the journal" or "do it for real and save it". store.rs is the private filing cabinet where the runtimes keep those journals and the in-memory mailboxes. Read them in that order — oracle first (the interface), ctx second (the logic), store third (the plumbing).

06oracle.rsthe only door randomness can walk throughcrates/pragmatic/src/oracle.rs

An oracle is this codebase's name for an LLM call: a prompt goes in, one sampled answer comes out. This file defines the tiny trait for that, plus a provenance label saying which model answered — audit metadata, never checked during replay. The rule is stated in the file itself: the oracle is the only source of unpredictability in a run. Everything random walks through this one door, so the journal only has to record what came through it. In replay mode the runtime never calls the oracle at all.

It also ships four ready-made oracles. SeededOracle makes random-looking answers from a starting number (a seed) — realistic test unpredictability at zero API cost. CountingOracle wraps any oracle and counts live calls; it is how tests prove replay makes zero model calls rather than just claiming it. RetryOracle retries only failures of the model call itself (rate limits, overload), doubling the wait each attempt — and retries happen before anything is journaled, so the journal keeps only the answer that finally succeeded. RefusingOracle errors on every call; strict replay runs against it, so "the model is never consulted" is enforced by construction, not convention.

Remember

Everything unpredictable enters through Oracle::call, and that is what makes "record once, replay forever" possible.

Questions you might get asked
  • Q: What happens when the model provider rate-limits us mid-run? A: RetryOracle catches exactly that kind of failure and tries again, waiting twice as long each time, up to a set limit. Any other failure passes straight through — it means the run is wrong, not the call.
  • Q: How do you prove replay never quietly calls the model? A: Two ways. Tests count live calls with CountingOracle and check for zero, and strict replay uses RefusingOracle, which errors on any call. Enforced, not promised.
  • Q: Do your tests burn API credits? A: No. SeededOracle gives repeatable fake answers from a seed — tests only. Production oracles are real model clients you implement.
07ctx.rsthe referee between your agent and the worldcrates/pragmatic/src/ctx.rs

Ctx is the object handed to your agent code. Every time the agent wants something from outside — a model answer, a tool call, a message, the current time — it asks Ctx, which decides step by step: serve the saved outcome from the journal (replay), or do it for real and save it (record). The agent cannot tell which happened. A resumed run replays its saved steps, then falls through to recording fresh, automatically.

Two safety features matter most. First, replay is checked, not blind: if the code asks a different question on replay than it did on record, the run fails loudly with JournalDesync instead of serving a stale answer — and program_marker records the program's name and hash, so replaying with changed code fails the same way. Second, external writes (send an email, charge a card) follow a write-ahead discipline: journal the intent to disk, then act, then journal the result. A crash in the middle leaves a dangling intent — proof the world may have changed — and the framework refuses to resume until it is resolved. It never guesses.

Remember

One code path, two meanings: the journal cursor decides, per step, whether reality is read back or written down.

Questions you might get asked
  • Q: What if the server dies right after charging a customer's card? A: The "about to charge" record is already on disk. On restart the framework halts and asks you to declare, through a recovery policy, whether the charge happened or should be written off — it never silently charges twice.
  • Q: Two disk writes per external action — isn't that slow? A: Yes, and it is deliberate. The intent must be durable before the world changes, or a crash could leave a payment with no record. That is the price of the guarantee.
  • Q: Can a developer bypass all this and read the clock directly? A: The compiler cannot stop it. The contract is that outside input goes through Ctx, backed by tripwires — the program hash check, the loud mismatch failure. It is a discipline with alarms, not a mathematical lock.
08store.rsthe filing cabinet behind both runtimescrates/pragmatic/src/store.rs

JournalStore is where both runtimes keep their journals and message inboxes. It is marked pub(crate) — private plumbing users never see — and shared by the sync Runtime and the async AsyncRuntime, so both get identical storage behavior. It loads or creates journals — in memory, or one append-only file per run on disk — passes along the key that lets journals be cryptographically chained and signed, and cleans run ids into safe filenames so a hostile id cannot escape the storage folder.

Its one public piece is the recovery vocabulary — your two choices for each effect a crash left half-finished:

pub enum Recover {
    Commit(Value),
    Compensate,
}

Commit(result) means "it happened — record this result, never redo it." Compensate means "write it off — the resumed run performs it fresh." The store also holds channel messages in memory. A message the agent actually received was journaled at that moment and survives crashes; a message sent but not yet received is lost in a crash. The durability line sits at consumption, not delivery — a deliberate boundary.

What the tests prove

Of these three files only oracle.rs carries inline tests: they show retries are bounded, the delays double correctly, and only transient model failures get retried. ctx.rs and store.rs are covered by runtime-level tests elsewhere in the crate.

Remember

The store makes journals durable and shared; messages are only as durable as the journal entry that consumed them.

Questions you might get asked
  • Q: If we crash, what does a customer lose? A: Nothing that was journaled — journals live on disk, and every step the run consumed is in them. Un-received messages vanish; a sender needing guaranteed delivery should send through a durable effect or redeliver on resume.
  • Q: Can two runs end up in the same file? A: In theory yes — filename cleaning is lossy, so two odd run ids could map to one file. In practice run ids are unique identifiers chosen by the caller; cleaning is for filesystem safety, not uniqueness.
  • Q: Why hide this file from users? A: No pub means no promise: its internals can change freely without breaking anyone. Users only ever see Runtime.
Part 4

Core crate III — the drivers (runtime, async_runtime, supervisor, memory)

The last module was the parts; this one is the machines that drive them: the engine that records, resumes, and replays runs, its async twin, the supervisor that handles crashes and undo, and a standalone labeled memory store that nothing else calls yet. Read them in that order.

09runtime.rsthe sync engine: record, resume, replaycrates/pragmatic/src/runtime.rs

Think of Runtime as a tape deck for agent runs. run records to tape while the agent executes. resume picks up a half-finished tape and keeps recording where it stopped. replay plays the tape back with the microphone unplugged — the model cannot be consulted. ("Sync" means ordinary one-step-at-a-time code.) The file mostly delegates: Ctx from the previous module does the per-step work, JournalStore does the storage. Every verb returns a RunReport, a receipt: what the run produced, and how many steps came from tape versus fresh from the model.

All three verbs share one engine, and two details carry the guarantees. In replay mode the model client is swapped for RefusingOracle, whose only job is to error — even a bug can't reach the network. The journal hits disk before the result is reported, so a failed attempt still leaves durable progress for resume.

Remember

All three verbs run the same agent code through the same engine; only the setup differs — whether a journal may be created, whether half-finished effects get cleaned up first, and whether the model is replaced by one that refuses.

Questions you might get asked

Q: You say replay never calls the model. Is that a promise or a hope? A: It's enforced twice: replay errors the moment the recording runs out, and even if that broke, the stand-in client errors on every call. A 1,000-run test counts model calls and asserts zero.

Q: What happens if a run crashes halfway through? A: Everything recorded so far is already on disk; resume redoes only what was lost.

Q: Can one Runtime handle many runs at once? A: No — single-owner by design; use one per thread or add a lock.

10async_runtime.rsthe same engine, with await (and a pocket executor)crates/pragmatic/src/async_runtime.rs

"Async" is Rust's way of writing code that can pause while waiting — say, for a model's answer over the network — instead of holding everything up. This file re-delivers the sync runtime's guarantees for async agents without adding a single outside dependency. It doesn't copy the logic: it wraps the sync Ctx for the journal bookkeeping and adds one new path for fresh model calls. That path checks the recording first, and in strict replay it fails before it could reach the network — the same guarantee as the sync engine, enforced at the same choke point.

Two conveniences round it out. Every sync model client automatically works as an async one (it just blocks while it runs — fine for tests and command-line tools; servers should implement the async version natively). And block_on, a roughly 20-line "executor" — the small loop that drives async code forward — means users don't need tokio, the big third-party async engine.

Remember

The async runtime doesn't fork the logic — it wraps the sync engine over a permanently refusing model client and routes fresh calls through one new path that checks the recording first.

Questions you might get asked

Q: Why build your own executor instead of using tokio? A: It keeps the zero-dependency claim, and tokio users lose nothing — the code runs on any executor. The pocket one has no timers or network handling, so servers should keep their real one.

Q: The sync engine swaps in a refusing model for replay. Does the async one have the same protection? A: Yes, arranged differently: the fresh-call path only runs when the replay check finds nothing, and in strict replay that check errors first.

11supervisor.rsthe crash boss: fault in, decision outcrates/pragmatic/src/supervisor.rs

When a run faults, someone must decide what happens next. That's the Supervisor, which maps each fault to one of four decisions:

pub enum Decision { Restart, Compensate, Escalate, Stop }

The default policy splits faults into two families. Transient ones — a flaky model, a flaky tool, a timeout — get restarted; trying again might work. Logical ones — a blown budget, a violated contract — stop; retrying would fail the same way. Every restart resumes from the journal, so a retry never redoes earlier model calls or effects. You can raise the retry cap (default 3), swap the policy, and plug in a "compensator" — your undo procedure.

The compensator drives the saga: real-world effects are undone in reverse order, like unwinding a stack, and each undo is journaled — so a crash mid-undo never undoes anything twice.

Remember

The supervisor never re-executes work — restarts resume from the journal and undos are journaled too, so both are safe to repeat.

Questions you might get asked

Q: What if an undo itself fails — the refund doesn't go through? A: The supervisor can't see that; it records the undo as done regardless. If your undo can fail, handle retries inside it — the journal still shows what was attempted, in what order.

Q: Retrying a down API three times fast — no waiting between tries? A: Deliberate — the supervisor caps attempts but owns no timing. Waiting belongs in the model-client layer, per call rather than per run.

Q: Undos are matched to effects by name — what if two share one? A: Only the recorded result tells them apart; give distinct actions distinct names. Simple keys won over something fancier.

12memory.rsa labeled store where secrets can't leak downhillcrates/pragmatic/src/memory.rs

A small key-value store — labeled slots you read and write by name — where every entry is marked Low (public) or High (secret). Two rules hold on every access: no read-up (a public-level reader can't see secrets) and no write-down (a secret-level writer can't create public-visible entries). Secrets ride the elevator up, never down. Both rules boil down to one less-than-or-equal comparison on a two-variant enum.

Two honest facts. Memory is deliberately not journaled: its contents can be rebuilt exactly by re-running the program against the recorded inputs, so saving them would only bloat the journal. And nothing else in the crate calls this file yet — it's a standalone, tested embodiment of the security rules from the research paper behind the design.

What the tests prove

Replay makes zero model calls over 100 random runs, resuming after a cut-short journal redoes only the lost part, and file-backed runs survive a process restart. Memory's own tests pin both security rules.

Remember

Both security rules reduce to one comparison — and the store is intentionally neither journaled nor yet wired into the runtime.

Questions you might get asked

Q: Does the product actually use this today? A: Not yet. It's exported but nothing in the runtime calls it — a working, tested demonstration awaiting integration, and saying that plainly is the defense.

Q: Real systems need more than two secrecy levels, right? A: True. Two is the smallest model that shows both rules, and the code is written against the general rule, not the two names — so richer labels are an extension, not a rewrite.

Q: Isn't "not journaled" a gap in the durability story? A: No — replay re-runs the program against the recording and memory comes out identical.

14lib.rsthe entire macro, 143 linescrates/pragmatic-macros/src/lib.rs

This file is the whole crate, and it acts like a notary: it never changes what a function does. When a developer writes #[pragmatic::durable] above an agent function, it fingerprints the source — a short hash, a number computed from the text that changes whenever the code really changes — and inserts one line at the top:

ctx.program_marker("research", "a1b2...")?;

On the first run, that line records the function's name and fingerprint as the journal's first entry. On replay it checks them: if the code changed, the run stops with a clear error before any step executes. Reformatting is harmless — whitespace and plain comments are stripped before the macro sees anything — but any real edit locks out old journals. That is the feature, not a bug.

Remember

The macro turns "replay the same code you recorded" from a promise into a check — one hash, one injected line.

Questions you might get asked

Q: The fingerprint isn't a cryptographic hash. Is that a security hole? A: No — it is a change detector, not a security boundary. Anyone able to tamper with the source could just rewrite the journal instead; tamper evidence belongs in the audit layer.

Q: Isn't reading code without a real parser fragile? A: There are known edge cases, but the failure is always a build-time error, never silently wrong code — and the fix, if needed, is a real parser behind the same public attribute.

Q: Could old journals stop replaying by accident? A: Real edits invalidate them by design; reformatting does not. One caveat: a compiler upgrade could in principle reprint the code differently and do the same — even then the failure is a loud error, never a silent replay of the wrong code.

Part 7

The C ABI — pragmatic-ffi

pragmatic-ffi is how every language that isn't Rust gets to use Pragmatic: it compiles to a library any C-speaking language can call, and the in-tree C++, Java, Go, and Node bindings all stand on it. Read include/pragmatic.h first — it is the promise — then src/lib.rs, which is how the promise is kept.

17pragmatic.hthe published contract, written by handcrates/pragmatic-ffi/include/pragmatic.h

This file is Pragmatic's promise to everyone who doesn't write Rust. A header is a short text file listing the functions a library offers and the rules for calling them. Ours is written by hand — no generator — because the most valuable parts are plain-English rules no tool could write: who frees each piece of text memory, that callbacks (code of ours that Rust calls back into) must never crash across the language border, and that a runtime must be used from one thread at a time — a thread being one of several independent workers a running program can have; only one worker may ever touch a given runtime.

It also hides our internals. The types callers hold — PragRuntime, PragCtx, PragReport — are opaque: declared but never described, so other languages carry a handle to them without seeing inside. That lets us rework the Rust side without breaking anyone. The header also lists the numbered error codes — PRAG_OK plus the PRAG_ERR_* family, most with a one-line meaning. Reading that list is the fastest tour of everything that can go wrong in a run.

Remember

This header is maintained by hand, so every change to the library's public surface must be mirrored here by a person.

Questions you might get asked

Q: A hand-written header sounds fragile — what catches a mismatch? A: Our automated builds compile the C++ and Go bindings — which read this header — against the freshly built library, so a drifted function breaks loudly. The Java and Node bindings copy the declarations by hand and miss that check; an honest gap.

Q: Can one runtime be used from several threads? A: No — the header says so plainly, and each language binding adds its own locking where needed. We can loosen this later without breaking the contract.

Q: If you rewrite the internals, do customer integrations break? A: No. Callers hold opaque handles and use only the functions listed here, so as long as the header keeps its promises, the inside can change freely.

18lib.rsthe whole C ABI in one filecrates/pragmatic-ffi/src/lib.rs

This file is the border checkpoint between the safe Rust runtime and every other language — the "C ABI" is the plain calling format they all speak. Nothing new is computed here: every function checks what crosses the border, copies text into memory the library owns, and stamps a numbered status code on the way out. The library frees its own text memory because the two sides may manage memory differently, and mixing memory managers crashes unpredictably.

A model callback from another language is wrapped so the runtime treats it as native. The context handle a caller uses during a run is disabled the moment its callback ends, so late use gets a clean error instead of a crash. Error types survive the crossing — "budget ran out" arrives as a different code from "tool flaked" — so callers still know what is safe to retry. And a Rust panic is caught and turned into an error code, because a panic must never cross the language border.

What the tests prove

tests/c_abi.rs uses the library exactly as a foreign language would: a run is recorded, resumed with zero fresh model calls, replayed with an identical trace, and verified for tampering — and typed errors and channel messages arrive intact.

Remember

Every trick in this file has the same shape: replace a silent memory error with a loud, typed, recoverable one.

Questions you might get asked

Q: Should the amount of unsafe code here worry me? A: It marks where the compiler can't check pointers from other languages, so the file checks them itself — verify on entry, disable after use, catch panics. A discipline, not a compiler guarantee.

Q: Can it carry raw binary data? A: Not yet. Text round-trips perfectly, but a C string ends at the first zero byte, so binary bytes become a placeholder character; buffer-style APIs are a known 0.x gap.

Part 8

The other languages — pragmatic-python and bindings/

These five files are how every language that is not Rust reaches the same Rust runtime. Python is the odd one out — it plugs into the Rust core directly instead of going through the C ABI; the other four (C++, Go, Java, Node) all sit on the C ABI and each re-solves the same two border problems with its own tools: who owns each piece of text that crosses, and how our code gets called back from the other side. Read Python first, then the C++ header, which sets the pattern the Go, Java, and Node files copy.

19pragmatic-python/src/lib.rsPython talks straight to the Rust corecrates/pragmatic-python/src/lib.rs

Every other language in this module reaches the runtime through the C ABI. Python does not. This crate uses PyO3 — a Rust library that turns Rust structs into real Python classes — to plug Python straight into the core crate. The result is a native-feeling package: you type import pragmatic and get real classes, and one built package (a "wheel") works on every Python from 3.9 up.

Python gets this because it is the first-class SDK, and going direct avoids translating everything twice (Rust to C text to Python). There is one carefully fenced piece of unsafe Rust: during a run, Python holds a raw memory address for the run's context object, and the binding blanks that address the instant the run ends. Stale use gets a clear error, not a crash.

Remember

Python binds the Rust core directly through PyO3, and the only unsafe code is one pointer that is deliberately blanked the moment its run ends.

Questions you might get asked
  • Why doesn't Python go through the C ABI like the other four languages? Python is the first-class SDK, so it gets a direct binding with real Python classes and no double translation. The C ABI exists for languages we only maintain.
  • Is the unsafe code a liability? It is contained: the pointer is pinned to one thread, blanked before the object goes away, and checked on every use. Misuse produces a loud Python error, not a crash.
  • What do errors look like for a Python user? Every runtime fault arrives as a plain RuntimeError carrying message text, so the typed fault code is flattened away. Richer exceptions could be added later without breaking anything.
20pragmatic.hppthe C ABI wrapped once; the pattern the other three copybindings/cpp/pragmatic.hpp

A single C++ header file: a customer includes it, links our library, and is done — nothing extra to compile. It wraps the raw C ABI in classes that clean up after themselves and turn error codes into ordinary exceptions.

It matters beyond C++ because it sets the two border rules the other bindings copy. Rule one: every string crossing the border has exactly one owner — anything Rust hands over is copied out, then handed back for Rust to free. Rule two: no exception may ever escape into Rust, because an exception crossing the border is undefined behavior — the program may do anything, including corrupt data. So every callback (code of ours that Rust calls back into) runs inside a catch-everything guard that turns failures into error messages. take is rule one in four lines:

inline std::string take(char* s) {
    if (s == nullptr) return {};
    std::string out(s);
    prag_str_free(s);
    return out;
}
Remember

Two rules — every string goes through take/give, and nothing ever unwinds into Rust — and the other three bindings are this file translated.

Questions you might get asked
  • Why does it matter that this is one header file? Zero build friction: one include line, one link flag. At this size the compile cost is trivial.
  • What if a customer's own code throws an error inside a callback? The guard catches it and hands Rust an error message, which the runtime records as a typed fault. Nothing crosses the border raw.
  • Why do the Go, Java, and Node files look so alike? Deliberately — this file sets the pattern and the others translate it, so fixes port easily.
21pragmatic.gothe same surface through cgobindings/go/pragmatic.go

One Go file binds the C ABI using cgo, Go's built-in bridge to C: a special comment in the file holds real C code and build settings. Border rules are the same as the C++ header. The twist: Go bans two things from crossing into C — its function pointers, and its pointers — because Go's garbage collector (its automatic memory cleaner) may move or free anything C still holds.

It works around both bans the sanctioned way. Tiny fixed C functions ("thunks") stand in for Go functions, and each Go closure is checked into a table that returns a ticket (cgo.Handle); C carries the ticket, Go redeems it when called back — a coat check. One honest wart: the numeric fault codes are hand-copied from the C header — Java and Node keep copies too — so renumbering a code touches three files.

Remember

Everything odd here exists because Go forbids its functions and pointers from crossing into C; thunks plus tickets are the approved workaround.

Questions you might get asked
  • Could a customer ship this binding in production? Not as-is: the build settings point at our development tree so tests run with zero setup. A real deployment would link an installed library; the README marks this binding maintenance-only.
  • What if the hand-copied error numbers drift out of sync? A fault would show the wrong label in Go, Java, or Node. The smoke tests assert on specific typed faults, so drift trips them.
  • Why a coat-check ticket instead of passing the function directly? Go's garbage collector cannot see what C holds, so the function could be freed while C still points at it. The ticket keeps it alive and findable.
22Pragmatic.javapure Java over the C ABI, no JNI to compilebindings/java/pragmatic/Pragmatic.java

One Java file binds the C ABI with java.lang.foreign, Java's built-in bridge to native code: it describes each C function's shape at run time and gets back a callable handle. The payoff: no JNI, the older approach that means compiling and shipping separate C glue per platform — here the standard Java compiler is the whole build.

The big deviation is how callbacks travel. C++ and Go smuggle the callback through a spare pointer that rides with each call; Java parks it in a per-thread slot (a ThreadLocal) and reads it back when Rust calls in. That works only because the runtime always calls back on the same thread — so one thread can drive only one run at a time. Two rough edges: the last oracle reference lingers in its slot until the next run (bounded, not a growing leak), and a RunReport holds native memory that leaks unless closed.

Remember

Java parks each callback in a per-thread variable instead of a pointer — safe only because the runtime always calls back on the same thread.

Questions you might get asked
  • Why require such a new Java version? JDK 22 is where java.lang.foreign finalized. The alternative is JNI: per-platform compiled glue, the exact burden this binding exists to avoid.
  • What is the riskiest part of this file? The C function shapes are written by hand and no compiler checks them; a mistake corrupts memory at call time, not build time. That is the tax for skipping JNI.
  • Does "one run per thread" limit customers? One thread cannot drive two runs at once, and callbacks must stay on their thread. Documented, and it matches how the runtime calls back.
23pragmatic.jsthe C ABI from Node via koffibindings/node/pragmatic.js

Node.js has no built-in way to call C, so this binding uses koffi, a package that loads our library from plain-text declarations of each C function, found via the PRAGMATIC_LIBRARY environment variable (an external setting) or defaulting to our development build.

Two ideas keep it tidy. First, string ownership is automated: koffi's "disposable" return type decodes each Rust-owned string and frees it in one step, so forgetting to free is impossible. Second, errors take a side door: when a JavaScript callback throws, the binding parks the original Error in a private slot and rethrows that exact object — stack trace intact — once the run returns the matching fault. Much nicer for debugging, and safe only because Node runs all JavaScript on one thread.

What the tests prove

Every language runs the same smoke test — record a run, resume with zero new model calls, replay bit-for-bit, verify the hash chain — proving journals are byte-compatible no matter which language recorded them.

Remember

JavaScript errors bypass the normal error slot and re-emerge as the original exception — a trick that is only safe because Node is single-threaded.

Questions you might get asked
  • Why do Node developers get real stack traces back when other languages don't? The normal error channel only carries text, so other bindings flatten the error; Node parks and rethrows the original object. The price is a single-threaded assumption, which matches how Node runs.
  • Why do timestamps come back as awkward BigInt values? Nanosecond timestamps are too big for JavaScript's ordinary numbers, which are only exact up to 2^53. A plain number would silently corrupt journaled clock reads.

Theorem T1 says replay reproduces the recorded run exactly; it is proved on paper in the calculus and demonstrated empirically by the 1000-run E1 suite. A Lean 4 mechanization is in progress — the semantics and the theorem statements are formalized, the proof bodies are not yet discharged — so it is not machine-checked today. The page explains the two modes every step runs in (record vs. replay), the Journal format (append-only, entries keyed by position, linked by SHA-256 hashes so any edit breaks the chain), the write-ahead effect discipline, program identity (your function's source is hashed and journaled as step zero, so changed code refuses to replay old journals), faults and the Supervisor, budgets and effect allowlists, and labeled memory for information-flow control. It closes with honest scope: one process, local files. Why it matters to you. When a technical buyer asks "why should I believe the guarantees," this page is the answer.

Appendix

Defending the whole system

These are the big-picture questions — the ones that span the whole system. The per-file Q&As handle the local stuff; these are what a skeptical engineer, an auditor, or an investor asks about the product as a whole. Answers are short on purpose: each one is something you can actually say in a meeting.

Q: Why does the core have zero dependencies? Isn't that just showing off? A: It's a trust argument. The pitch is "this journal is your audit trail" — and an audit trail is only as trustworthy as the code that wrote it. Our core is small enough to read in an afternoon, with no third-party code inside it that an auditor would also have to vet. The trade-off: we had to build a few things ourselves that most projects import, and we accept that cost deliberately. The two model adapters are the documented exception — they need HTTPS and JSON, so they use two well-known libraries, kept at the edge.

Q: You wrote your own SHA-256? Isn't rolling your own crypto a famous mistake? A: The famous mistake is inventing your own scheme — new algorithms, new protocols. We didn't. SHA-256 is a public, standardized recipe with official test answers published by the US government (NIST), and our implementation is automatically checked against those answers in our test suite. It's used for fingerprinting log entries, not for keeping secrets. And if we ever want a third-party implementation instead, it's a one-file swap.

Q: AI models give different answers every time. How can replay be "exact"? A: Because replay never asks the model anything. When the run happens, we save the model's actual answer — the exact bytes. Replay re-runs the agent's code and hands back those saved answers. During an audit replay the model is literally replaced with a stub that errors if anyone tries to call it. The randomness isn't eliminated; it's captured the moment it happens and never consulted again.

Q: What stops someone from editing the log after the fact? A: Every entry is fingerprinted together with the fingerprint of the entry before it, forming a chain. Change anything and every later fingerprint stops matching — the verify command points to the exact spot where the chain breaks. Honest framing: this makes tampering detectable, not impossible. For stronger protection there's an option to mix a secret key into the fingerprints, so an outsider without the key can't rebuild a convincing fake chain.

Q: Can it handle many agents at once? A: Many runs at once, yes — every run has its own separate journal. Inside a single run, things happen one step at a time, on purpose: a recorder needs a clear, ordered story to replay. That's a stated design decision, not a limitation we stumbled into.

Q: Is there anything that does NOT survive a crash? A: One thing, by design: a message that was sent to a run but not yet picked up by it dies with the process. The rule of thumb: the journal records what the run observed, not what the outside world did. Anything that must survive should go through the recorded channels.

Q: Why does changing the agent's code break replay of old logs? A: On purpose. A journal is a recording of one specific version of your agent. Replaying it under different code would be a lie — so the runtime stamps a fingerprint of the code into the log's first entry and refuses to replay under anything else. The blunt edge: even a tiny code edit invalidates old recordings. Think of journals like build artifacts, tied to a version.

Q: Parts of this were AI-generated. Why should anyone trust it? A: Because trust here comes from the tests, not the author. The core promises — zero re-paid tokens on recovery, bit-for-bit replay, tamper detection — are all encoded as automated tests, including ones that record over a real network connection, kill the server, and prove replay works with the model unreachable. Every language binding runs the same story end-to-end. The code was also reviewed and is fully documented — this guide is part of that.

Q: What are those "T1" and "Lean" references in the comments? A: The design is based on a formal mathematical model (the team calls it the Agentical calculus), and its main theorem — replay reproduces the run exactly — is proved on paper in that calculus. Say it exactly this way: the math is proved on paper, and the Rust code is an implementation held to that math by the test suite (1000 of 1000 runs replay byte-identically), not a machine-verified program itself. There is a Lean 4 development, but it is a skeleton: the semantics and the theorem statements are formalized while the proof bodies are still sorry. Do not call it machine-checked or “sorry-free” — that is a specific, checkable claim in the Lean world, and it is the one thing here that would not survive a technical reference check.

Q: Give me the whole repo in five sentences. A: Every model call's answer is saved to an append-only, fingerprint-chained log the moment it happens. Crash recovery and audit replay are the same move — re-run the code, feed back the saved answers. The core does this with zero dependencies; adapters connect real model APIs; a small macro pins the code version; a CLI turns logs into readable web pages; a C layer carries it all to five other languages. Side effects are written down before they're performed, so they're never accidentally done twice. The journal is the product — everything else exists to write it, protect it, or read it.
