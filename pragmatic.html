Durable execution made software reliable. But its replay model assumes determinism, and LLM agents are not deterministic. Everyone else caches around that. We modeled it.

Three guarantees, every run

Journal every step.

Each LLM call's realized outcome is recorded to an append-only log as the run proceeds. The journal is the source of truth for what the agent actually did, not a reconstruction after the fact.

Recover from any crash.

Resume exactly where the agent stopped. Recorded outcomes are read back instead of re-sampled, so there are no duplicate model calls, no divergent paths, and no lost work after a failure.

Replay faithfully.

Reproduce the entire run exactly for debugging and audit, nondeterministic LLM behavior included. Replaying the journal reproduces the original trace, exactly, every time.

In your code

Durable in one wrapper.

Keep writing agents the way you already do. Wrap the run, route model calls through the Oracle, and Pragmatic journals every realized outcome as the agent executes.

Crash on step nine of a thousand and the agent resumes on step nine, reading every prior call back from the Journal instead of paying for it again.

Why Pragmatic

A model, not a cache.

Every durable execution engine handles a nondeterministic call the same way: run it once, cache the output as an opaque activity, and replay that fixed value. It works, but the engine never understands the call. Pragmatic models each LLM call as a first-class probability distribution and proves replay reproduces the run.

The LLM as an opaque activity

elsewhere

The model call is a black box. Its output is cached and replayed as a fixed value, with no notion of the distribution it came from.

Replay is sound only if you keep all surrounding workflow code deterministic by hand. Step outside that and you hit nondeterminism errors.

No way to reason about the probability a run meets its spec, and no guarantee about how secret inputs flow to public outputs.

The LLM as a first-class Oracle

at Pragmatic

The model call is a probability distribution the runtime understands. Replay soundness is mechanized in Lean 4, not left to discipline.

The determinism boundary is principled, so faithful replay holds across the whole run, nondeterministic behavior included.

Compositional probability bounds let you reason about whether a multi-agent system meets its spec, and noninterference is provable.

Anatomy

A runtime, not an operating system.

the runtime

A library, on your infrastructure.

Pragmatic runs on the infrastructure you already have: Linux, containers, any cloud. It links into your agent as a library. There is nothing new to provision and no operating system to adopt.

the core

Oracle and Journal.

Each LLM call is modeled as a probability distribution, the Oracle. Every realized outcome is written to an append-only Journal. Replay reads outcomes back instead of re-sampling the model, which is what makes recovery faithful.

trust

Capabilities and a signed log.

Every effect carries a capability token, and the Journal is a signed, immutable record of the run. Idempotency, provenance, and a tamper-evident audit trail, at the runtime level.

control

The Supervisor.

The Supervisor detects failures, restores agents from their Journals, and drives recovery and replay. It turns a crashed run into a resumed one without re-sampling or lost work.

Research

Agentical, the theory behind the runtime.

Pragmatic's guarantees are real because they are proved. Agentical is the probabilistic process calculus underneath the runtime: the reason crash recovery and faithful replay hold even when the model underneath is nondeterministic.

Durable execution is the proven substrate for reliable software: Temporal, Restate, Inngest, and DBOS all build on it. But its replay model assumes code is deterministic, so every engine works around LLMs by caching model outputs as opaque activities. Frontier models show only 50 to 96 percent determinism even at temperature 0. Pragmatic is durable execution built for nondeterminism from the ground up, holding durable replay, crash recovery, and information-flow reasoning together.

Model each LLM call as a probability distribution. Journal every realized outcome. Recovery becomes replay.

Two nondeterminisms are kept cleanly separate: probabilistic, resolved by the Oracle, and adversarial scheduling, resolved by a scheduler, the standard probabilistic-automata setup. The calculus itself is π-calculus-style, with a probabilistic small-step operational semantics in record and replay modes, over six primitives: Agent, Oracle, Channel, Memory, Journal, and Supervisor. A configuration is the 5-tuple <P;H;J;K;t>: agent pool, shared store, journal, channel state, and logical clock.

Three theorems, honest scope

T1, proved and mechanized in Lean 4

Replay soundness, the flagship result: replaying the recorded journal reproduces the original run's trace exactly, with probability 1, via a coupling on the shared oracle-randomness space.

T2, proved on paper

Probabilistic noninterference: secret inputs don't affect public observations, conditional on per-label oracle partitioning and a label-filtered scheduler.

T3, proved on paper

Compositional bounds: local per-agent probability contracts compose to a global union bound, with a Fréchet–Hoeffding fallback when independence fails.

From proof to running code

The Lean 4 mechanization covers T1's operational core, trace-equivalence, crash-resume, no-orphaned-effect, and cursor-determinism, all sorry-free. Channels, the measure-theoretic layer, and T2/T3 are not yet mechanized, and we say so.

The Rust runtime is a zero-dependency reference implementation. Six integration tests demonstrate the three properties. Measured: 1000 of 1000 replay-determinism runs; ~230 ns constant-time journal append, flat to a million entries; and a ~1500× replay speedup under a latency-injected oracle, since replay performs zero model calls.

Questions

How is this different from a general durable execution engine?

+

General durable execution treats a model call as an opaque step: run it once, store the output, replay the stored value. That works well, and we build on the same lineage. The difference is that the engine has no model of the call, so there is no probabilistic reasoning and no information-flow guarantee, and replay holds only while the surrounding code stays deterministic. Pragmatic models the call itself and proves the replay guarantee.

How can replay be faithful if LLMs are nondeterministic?

+

Pragmatic does not re-sample the model on replay. The first run records each realized outcome to the Journal, and replay reads those outcomes back. Reproducing a run reads from the log rather than calling the model again, which is what makes it exact.

Do I have to rewrite my agent?

+

No. Keep your agent logic and route model calls through the Oracle. The runtime links in as a library and journals outcomes as the agent runs. There is no new operating system and no new orchestration language to learn.

Is it production-ready?

+

Pragmatic is in private beta with design partners. The replay guarantee is mechanized in Lean 4 and the Rust reference runtime passes its determinism and recovery tests today. The probabilistic and information-flow results are proved on paper and not yet mechanized.

Where does my data live?

+

With self-hosted, the runtime and your Journals stay entirely in your environment. Pragmatic Cloud manages durable journaling and replay for you. Enterprise adds a signed, immutable audit trail and information-flow guarantees for regulated teams.
